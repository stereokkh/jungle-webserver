# 사용법과 지원 범위

서버를 띄우고 쓰는 사람을 위한 문서다. 모듈 사이 약속은 `docs/interfaces.md`, 결정 이유는 `docs/decisions.md` 에 있다.

## 실행

```bash
./webserver -p <port> -r <docroot> [-c <proxy.conf>] [--merge-slashes]
```

| 인자 | 뜻 |
|---|---|
| `-p` | 듣는 포트. 1-65535 의 10진수, 앞자리 0 불가 (`08080` 거절). `X-Instance` 헤더 값으로 그대로 쓰인다 |
| `-r` | 정적 파일 루트 폴더. 없거나 폴더가 아니면 시작하지 않음 |
| `-c` | Reverse Proxy 설정 파일 (선택). 형식이 틀리면 `파일:줄: 이유` 를 찍고 시작하지 않음 |
| `--merge-slashes` | 경로의 빈 조각 `//` 를 400 대신 `/` 하나로 합친다 (선택). nginx `merge_slashes` 와 같은 동작이지만 **기본값이 반대** (nginx 는 기본으로 합침, 이 서버는 기본으로 400) |

- 잘못된 인자는 서버를 띄우기 전에 exit 1
- IPv6 소켓 하나로 IPv4 까지 받는다 (`127.0.0.1`, `::1` 모두 접속 가능)
- `Ctrl-C`(SIGINT)·SIGTERM: 새 연결을 받지 않고 열린 연결을 정리한 뒤 exit 0

## 요청 처리 순서

```
요청 → ⓪ 정확히 /healthz 인가                → 헬스체크 (이 서버가 직접 200 ok)
     → ① 프록시 라우트에 맞나 (-c 가 있을 때) → 백엔드로 전달
     → ② /api/ 로 시작하나                    → 내장 앱
     → ③ 그 외                                → docroot 정적 파일
```

⓪~③ 은 모두 파서가 만든 **경로 정규형**에서 나온다. ⓪·①·② 는 정규형의 `?` 앞을 바이트 그대로 비교하고, ③ 은 정규형을 끝까지 디코딩한 경로로 파일을 연다. 그래서 `//admin/x`, `/%61dmin/x` 같은 표기로 라우트를 건너뛸 수 없다.

| 요청 경로 | 결과 |
|---|---|
| `/%61pi/echo` | `/api/echo` 와 같음 (비예약 문자 `A-Z a-z 0-9 - . _ ~` 의 `%XX` 는 글자로) |
| `/a%eb` | `/a%EB` 로 정규화 (나머지 `%XX` 는 16진수 대문자) |
| `/a%2Fb`, `/a%5Cb`, `/a\b` | 400 (구분자로 읽힐 수 있는 바이트) |
| `//a`, `/a//b`, `/a//` | 400. `--merge-slashes` 면 `/a`, `/a/b`, `/a/` |
| `/a/../b`, `/a/%2E%2E/b` | 400 |
| `/a%00`, 잘못된 `%XX` | 400 |

`?` 뒤 query 는 정규화하지 않고 원본 그대로 둔다. 순서·이유는 `docs/decisions.md` 2026-11-23.

## 정적 파일

- 메서드: GET, HEAD. 그 외는 405 `Allow: GET, HEAD`
- 폴더를 요청하면 그 안의 `index.html`
- 없으면 404. docroot 밖으로 나가는 경로(`..`, docroot 밖을 가리키는 심볼릭 링크)·일반 파일이 아닌 것은 403. 파일이 있든 없든 같은 403 이라 docroot 밖 파일이 있는지 새지 않는다
- 경로에 `.`·`..` 조각, 빈 조각 `//`, `%2F`·`%5C`·`\` 가 있으면 파서가 400 (위 "요청 처리 순서" 표)
- Content-Type 은 마지막 확장자를 대소문자 무시로 본다: html/htm, css, js, json, txt, png, jpg/jpeg, gif, svg, ico. 모르면 `application/octet-stream`. text 계열은 `charset=utf-8`
- 큰 파일도 메모리에 다 올리지 않고 나눠 보낸다

## 헬스체크 (`/healthz`)

| 요청 | 응답 |
|---|---|
| `GET /healthz`, `HEAD /healthz` | 200 `ok\n`, `text/plain; charset=utf-8` (HEAD 는 본문 없이) |
| `/healthz` 에 GET·HEAD 외 | 405 `Allow: GET, HEAD` |

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://localhost:8080/healthz   # 200 이면 살아 있음
```

- **프록시보다 먼저** 본다. 프런트에 보내면 프런트가, 백엔드에 직접 보내면 그 백엔드가 답한다. `X-Instance` 로 누가 답했는지 확인할 수 있다. 프록시 설정에 `/` 라우트가 있어도 `/healthz` 만은 넘기지 않는다
- 정확히 `/healthz` 일 때만이다 (질의는 무시: `/healthz?probe=1` 도 됨). `/healthz/x`, `/healthzz` 는 헬스체크가 아니라 평소 순서(프록시 → 앱 → 정적)로 간다
- "이 서버 프로세스가 요청을 받아 응답할 수 있다"만 뜻한다. 백엔드가 살아 있는지는 보지 않는다
- docroot 에 `healthz` 라는 파일을 두어도 보이지 않는다 (헬스체크가 먼저)
- 2026-11-25 전에 있던 덧셈 `GET /api/add` 를 대신한다 (이제 404)

## 내장 앱 (`/api/`)

| 요청 | 응답 |
|---|---|
| `POST /api/echo` | 200 받은 본문 그대로 (`\0`·CRLF 포함), `application/octet-stream` |
| `/api/echo` 에 POST 외 | 405 `Allow: POST` |
| 그 외 `/api/` 경로 | 404 |

- 헬스체크와 앱까지 온 응답(오류 포함)에는 `X-Instance: <포트>` 가 붙는다. 프록시를 거친 응답에서 어느 백엔드가 답했는지 볼 때 쓴다. 파서가 먼저 거절한 응답(`PUT /api/echo` 의 501 등)과 정적 파일로 간 응답(`/api` 의 404 등)에는 없다
- 경로는 바이트 그대로 비교하므로 `/api/ECHO`, `/api/echo/` 는 404. `/api/%65cho` 는 정규형이 `/api/echo` 라 echo

## Reverse Proxy (`-c`)

설정 파일은 한 줄에 `접두사 host:port [host:port...] [옵션...]`, `#` 은 주석.

```
# /api 아래는 두 백엔드로 번갈아
/api 127.0.0.1:8001 127.0.0.1:8002

# /ha 아래는 주 백엔드 둘에 백업 하나. connect 가 실패하거나 1초 안에 안 끝나면 다음 백엔드로 넘어가고,
# 주 백엔드 둘이 다 안 되면 백업을 쓴다 (한 요청이 최대 3개까지 시도)
/ha 127.0.0.1:8001 127.0.0.1:8002 backup=127.0.0.1:8003 failover=connect,timeout tries=3
```

옵션 (`=` 가 있는 토큰. 접두사 뒤 어디에나 올 수 있고 백엔드 사이에 끼워도 된다):

| 옵션 | 뜻 | 없으면 |
|---|---|---|
| `backup=<host:port>` | 백업 백엔드. 이번 요청에 아직 시도하지 않은 정상(쉬는 중이 아닌) 주 백엔드가 없을 때만 쓴다. 여러 번 써도 되고 적은 순서대로 쓴다. 주 + 백업이 8개를 넘으면 오류, 주 백엔드가 하나도 없으면(백업만) 오류 | 백업 없음 |
| `failover=<목록>` | 쉼표로 나눈 `off`, `connect`, `timeout`. `connect`: connect 가 실패하면 다음 백엔드. `timeout`: connect 가 1초(`PROXY_CONNECT_TIMEOUT_MS`) 안에 안 끝나면 그 연결을 닫고 다음 백엔드. `off` 는 혼자서만 쓴다. 빈 항목·중복·모르는 값은 오류 | `off` (고른 백엔드가 안 되면 바로 502/504) |
| `tries=<N>` | 요청 하나가 시도할 백엔드 수 (첫 시도 포함). 1~8, 앞자리 0 없는 10진수. 모든 백엔드가 죽었을 때 응답이 늦어지는 것을 막는다 | 주 + 백업 전부 |

- `failover=`, `tries=` 는 한 줄에 한 번만. 모르는 옵션 이름, 빈 값, `=` 로 시작하는 토큰은 오류다 (`파일:줄: 이유`)
- `failover=off` 이거나 `failover=` 가 없으면 `backup=` 은 오류는 아니지만 **쓰이지 않고**, `tries=` 는 **효과가 없다** (예전 동작 그대로: 고른 백엔드가 안 되면 502)
- 요청을 업스트림에 **쓰기 전**의 실패(connect 오류·connect 시간 초과)에서만 넘어간다. 요청 바이트를 보내기 시작한 뒤의 실패는 넘기지 않고 502/504/연결 종료 그대로다. 그래서 POST 도 같은 요청이 두 백엔드에서 실행되는 일이 없다
- 전체 마감은 그대로다: 첫 시도부터 5초(`UPSTREAM_TIMEOUT_MS`)가 지나면 몇 번째 백엔드든 504. 시도를 다 썼을 때는 마지막 실패가 connect 오류면 502, connect 시간 초과면 504. 마감이 이미 지났으면 다음 백엔드에 connect 하지 않고 504
- 고르는 순서: 주 백엔드를 Round-Robin 으로, 다 시도했거나 쉬는 중이면 백업을 적은 순서로. connect 오류·시간 초과가 난 백엔드는 10초(`PROXY_BACKEND_DOWN_MS`) 동안 쉰다 (시간이 지나면 저절로 돌아온다). 라우트의 백엔드가 전부 쉬는 중이면 쉬는 표시를 무시하고 시도한다
- 넘어간 요청의 `Host` 는 실제로 보낸 백엔드의 이름이다

- 접두사는 `/` 로 시작. 경로 경계에서만 맞는다 (`/api` 는 `/api/echo` 에 맞고 `/apix` 에는 안 맞음). 여러 개가 맞으면 가장 긴 접두사
- 요청 대상은 **접두사를 떼지 않고** 정규형 그대로 백엔드에 보낸다 (`/%61pi/a%eb?x=%41` → `/api/a%EB?x=%41`). 판정한 경로와 백엔드가 받는 경로가 같다
- 백엔드 이름은 시작할 때 한 번만 해석하고 IPv4 를 먼저 고른다
- 한도: 줄 1024바이트, 접두사 127바이트, 라우트 16개, 라우트당 백엔드 8개
- 백엔드는 같은 바이너리를 `-c` 없이 다른 포트로 띄우면 된다 (`tests/backends.sh` 참고, #10 후속 PR 에서 추가)
- 백엔드로 보낼 때 hop-by-hop 헤더와 `Expect` 는 빼고, `Host`·`X-Forwarded-For`·`Via: 1.1 jungle-webserver`·`Connection: close` 를 새로 쓴다
- 중계 (#9): 백엔드가 응답 머리를 보내기 전에 실패하면 502 (연결 실패, 깨진·끊긴 머리), 머리가 `UPSTREAM_TIMEOUT_MS`(5초) 안에 안 오면 504. 응답이 시작된 뒤 실패하면 이미 받은 바이트까지만 보내고 연결을 닫는다. 응답은 머리를 고치지 않고 그대로 넘기고, 그 뒤 클라이언트 연결은 항상 닫는다 (keep-alive 없음). 요청을 보낸 뒤의 재시도는 없다 (넘기는 것은 위 `failover=` 로 connect 전에만)
- 라우트에 백엔드가 여럿이면 Round-Robin (요청마다 다음 주 백엔드). `failover=` 가 없으면 죽은 백엔드 차례에 502. 다시 쓴 요청 머리가 8192바이트를 넘으면 431

## 지원하는 HTTP 범위

| 항목 | 지원 |
|---|---|
| 버전 | HTTP/1.0, HTTP/1.1 (그 외 505) |
| 연결 | 1.1 은 keep-alive 기본, 1.0 은 close 기본. `Connection` 헤더를 따름. 파이프라이닝 |
| 본문 | `Content-Length` 만. `Transfer-Encoding`(chunked) 은 501 |
| 한도 | 요청 대상 2KB (414), 요청 라인+헤더 8KB (431), 본문 1MB (413) |
| 시간 | 요청이 30초 안에 다 오지 않으면 연결을 닫음 |
| HEAD | 헤더(Content-Length 포함)는 GET 과 같고 본문 없음 |
| 오류 본문 | `<h1>404 Not Found</h1>` 처럼 상태만. 요청 값은 넣지 않음 |
| 범위 밖 | CGI, Forward Proxy, 캐시, TLS, chunked, 요청을 백엔드에 보낸 뒤의 다른 백엔드로 재시도 (connect 전의 `failover=` 는 지원) |

응답 상태 코드: 200, 400, 403, 404, 405, 413, 414, 431, 500, 501, 502, 504, 505.

## 운영 제약

1. **백엔드 앱을 프록시로 쓰려면 라우트를 `/api` 로 묶는다.** 접두사를 떼지 않으므로 `/calc 127.0.0.1:8001` 로 묶으면 백엔드는 `/calc/add` 를 받고 앱이 아니라 정적 파일로 보내 404 를 낸다. 이 404 에는 `X-Instance` 가 없어 프록시 오류처럼 보인다
2. **백엔드는 IPv4 loopback 을 받아야 한다.** 프록시가 이름을 IPv4 로 먼저 풀기 때문이다. 같은 바이너리는 IPv4·IPv6 를 다 받으므로 따로 할 일은 없다
3. curl 로 큰 본문을 POST 하면 `Expect: 100-continue` 때문에 curl 이 1초 기다린 뒤 보낸다. 서버는 `100 Continue` 를 보내지 않는다. 지연이 싫으면 `-H 'Expect:'`
