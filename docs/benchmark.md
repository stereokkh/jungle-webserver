# 측정 기록 (#11)

정적 파일 처리량, CS:APP Tiny 와의 제한적 비교, 리버스 프록시 경유 처리량. 숫자는 **이 환경에서 관찰한 값**이고, "무엇 때문에 몇 배" 같은 인과는 주장하지 않는다 (CLAUDE.md). 다시 재려면:

```bash
make classic                 # (선택) Tiny 를 classic/ 에 빌드. 없으면 Tiny 칸은 건너뜀
bash scripts/bench.sh        # 3회 반복 중앙값, 결과는 표 형태로 stdout
REPS=5 N=20000 CONCS="10 100" bash scripts/bench.sh
BIN=/다른/빌드/webserver bash scripts/bench.sh   # 이 폴더를 빌드하지 않고 그 바이너리로 잼
```

## 환경과 조건

- WSL2 (Linux 6.18), Intel Core Ultra 5 125H, 논리 코어 18, 메모리 7GB, `ulimit -n` 10240 (동시성 1000 실패 수가 이 값에 따라 달라질 수 있음). 서버와 `ab` 가 **같은 기계**에서 돈다 (부하 도구도 CPU 를 씀)
- gcc 15.2 `-O2`. 우리 서버와 Tiny 모두 같은 최적화, sanitizer 빌드는 측정에서 뺌
- ApacheBench 2.3: 요청 10,000 개 × 3회, 표는 중앙값. `ab` 는 HTTP/1.0 으로 요청함
- 파일: 4,096 바이트 텍스트 하나. 측정 전에 두 서버 응답 본문이 원본과 **일치**함을 `cmp` 로 확인
- Tiny 는 요청마다 헤더를 stdout 에 찍으므로 `/dev/null` 로 보냄. 우리 서버는 접근 로그가 없음
- 측정일 2026-11-23, develop `ec8bece` (PR #36 업스트림 중계 포함) 빌드를 `BIN` 으로 지정

### 표에서 눈에 띄는 것

- **정적 파일을 keep-alive 로 받을 때 요청마다 약 44ms 멈춘다 (`/api/add` 는 멈추지 않음).** 동시성 1 에서도 초당 23 요청 (p50 44ms). 위 표의 keep-alive 처리량도 "동시성 ÷ 0.044초" 와 거의 같다 (10 → 227, 100 → 2,273). 같은 연결에서 이어 보낸 요청의 시간을 curl 로 재면 `/index.html` 은 두 번째부터 0.041~0.047초, `/api/add` 는 0.0002초 안팎. 정적 파일은 응답 머리를 `write` 한 뒤 본문을 `CONN_SENDING_FILE` 에서 따로 보내고, 앱 응답은 머리·본문이 한 버퍼라 `write` 한 번에 나간다. 그런데 accepted 소켓에 `TCP_NODELAY` 가 없다. 실험용 복사본에서 `accept` 직후 `TCP_NODELAY` 를 켜자 같은 조건이 동시성 1 → 8,302 요청/초, 10 → 38,381 요청/초, p50 0ms 가 됐다. Nagle 알고리즘과 상대의 지연 ACK 가 맞물린 것으로 본다. 수정은 이 문서 범위 밖 (`server.c`, 별도 PR)
- **동시성 1000, 연결 재사용 없음에서 실패 1,205.** (앞서 `dd09465` 에서는 1,432. 회마다 달라짐) 실패 종류는 `ab` 기준 Exceptions·Length (받던 연결이 끊김). 닫히는 중(LINGERING 등)인 연결까지 합쳐 `SERVER_MAX_CONNS`(1024) 에 닿으면 새 연결은 받자마자 닫힌다 (`accept_ready`). 실험용 복사본에서 상한을 4096 으로 올리자 같은 조건 3회 모두 실패 0. 상한에서 거절하는 것은 설계대로이고, 숫자를 바꿀지는 정하지 않았다
- Tiny 는 동시성을 올려도 요청/초가 약 1.1만으로 거의 같고 지연만 늘었다 (한 번에 연결 하나를 처리). 우리 서버와의 차이를 poll 하나의 효과로 읽으면 안 된다: Tiny 는 연결마다 `Getnameinfo`·`printf`, 파일마다 `mmap` 을 하고, 우리 서버는 하지 않는다

## 느린 연결이 있을 때

아무것도 보내지 않는 연결 하나를 열어 둔 채 `curl -m 5` 로 같은 파일을 요청:

| 서버 | curl 결과 | 그 뒤 |
|---|---|---|
| 우리 | 200, 0.0003초 | 200, 살아 있음 |
| Tiny | 응답 없음, 5초 타임아웃 | 열어 둔 연결을 닫자 **종료 (상태 141 = SIGPIPE)** |

Tiny 는 첫 연결의 요청 줄을 기다리느라 다음 연결을 받지 않고, 첫 연결이 끊긴 뒤 그 연결과 포기한 curl 에 응답을 쓰다가 끝났다 (`docs/classic.md` 1·2번).

## 잘못된 입력·연결 중단 뒤 생존

경우마다 서버를 새로 띄우고, 그 뒤 정상 요청 하나를 보냄:

| 경우 | 우리 | Tiny |
|---|---|---|
| 요청 줄이 HTTP 가 아님 (`HELLO`) | 200, 살아 있음 | 200, 살아 있음 |
| 대상 9,000 바이트 GET | 200, 살아 있음 | 종료 (상태 134 = SIGABRT) |
| 20MB 받는 중 0.3초에 끊음 | 200, 살아 있음 | 종료 (상태 0, `Rio_writen error: Connection reset by peer`) |

## 프록시 경유

같은 바이너리로 백엔드 2개(`-c` 없음)와 프런트 1개(`/api/ 127.0.0.1:18511 127.0.0.1:18512`)를 띄우고, `GET /api/add?a=1&b=2` (본문 `3`, 1 바이트)를 백엔드에 직접 / 프런트를 거쳐 보냄. 측정 전에 두 경로 본문이 같음을 확인. 연결 재사용 없음, 10,000 요청 × 3회 중앙값:

| 경로 | 동시성 | 요청/초 | p50 ms | p99 ms | 실패 / non-2xx / 전체 |
|---|---|---|---|---|---|
| 백엔드 직접 | 10 | 39,446 | 0 | 1 | 0 / 0 / 30,000 |
| 프런트 경유 (백엔드 2개) | 10 | 16,298 | 1 | 1 | 0 / 0 / 30,000 |
| 백엔드 직접 | 100 | 49,231 | 2 | 3 | 0 / 0 / 30,000 |
| 프런트 경유 (백엔드 2개) | 100 | 19,993 | 5 | 7 | 0 / 0 / 30,000 |
| 백엔드 직접 | 1000 | 35,305 | 26 | 39 | **825** / 0 / 30,000 |
| 프런트 경유 (백엔드 2개) | 1000 | 19,758 | 49 | 60 | **156** / 0 / 30,000 |

- 경유는 직접의 약 40% (동시성 10·100). 프런트는 요청 하나에 클라이언트 연결 + 업스트림 연결(새 `connect`, `Connection: close`)을 함께 다룬다. 어느 단계가 시간을 쓰는지는 이 측정으로 나누지 않았다
- 동시성 1000 실패는 정적 파일 표와 같은 종류 (받던 연결이 끊김). 백엔드·프런트 모두 연결 상한 1024 를 쓴다
- 프런트는 백엔드에 늘 `Connection: close` 를 보내므로 업스트림 연결을 요청마다 새로 연다 (`docs/decisions.md`). keep-alive 경유는 재지 않았다

## 한계

- 한 기계, WSL2, 3회 반복. 다른 기계나 네트워크 너머에서는 숫자가 다르다. 프록시 측정은 백엔드·프런트·`ab` 가 모두 같은 기계
- 정적 파일 하나(4KB)와 `/api/add` 하나만 잼. 큰 파일·여러 파일·큰 본문 중계는 재지 않음
- Tiny 비교는 "같은 파일, 연결 재사용 없음, 같은 최적화, 로그는 버림" 조건의 관찰이다. 구현 방식이 여러 군데 달라서 어느 차이가 숫자를 만들었는지는 이 측정으로 알 수 없다
