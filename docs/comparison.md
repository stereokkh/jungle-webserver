# 다른 방식과 비교

## 1. CS:APP Tiny

출발점이다. Tiny 를 직접 띄워 재현한 11가지와 코드에서 본 4가지를 어느 이슈·PR 에서 고쳤는지는 [classic.md](classic.md) 에 있다.

| 우리 파일 | Tiny | 바뀐 것 |
|---|---|---|
| `server.c` | `while (1) { Accept; doit; Close; }` | poll 이벤트 루프, keep-alive, 타임아웃, lingering close, 시그널 정리 |
| `net.c` | `open_listenfd` | exit 대신 -1, IPv6 소켓 하나로 IPv4 까지, 논블로킹 |
| `http_request.c` | 요청 줄 `sscanf`, 헤더는 읽고 버림 | 증분 파서, `Content-Length` 본문, 크기 제한, 경로 정규형 |
| `handler.c` | `strstr(uri, "cgi-bin")` 로 정적/동적 판단 | 경로 접두사로 프록시 → 앱 → 정적 |
| `http_response.c` | `clienterror` (요청 값을 HTML 에 그대로) | 버퍼에 조립, 요청 내용을 넣지 않음, `Content-Length` 항상 |
| `static_file.c` | `"."` 뒤에 URI 를 붙여 열고 `mmap` 한 번에 전송 | `..`·심볼릭 링크 탈출 403, 조각 전송 |
| `app.c` | `serve_dynamic` (CGI `fork`·`exec`) + `adder.c` | 서버 안 함수 호출, 숫자·범위 검사 |
| `proxy*.c` | 없음 | Reverse Proxy, Round-Robin, failover |

**가장 크게 다른 점**: Tiny 는 요청을 안 보내는 연결 하나에 `Rio_readlineb` 가 멈춰서 다른 모든 클라이언트가 기다린다. 우리 서버는 그 연결이 `READING` 에서 기다리는 동안 다른 연결을 계속 처리하고, 10초(유휴)·30초(요청) 뒤 끊는다.

| 관찰 (같은 기계, [benchmark.md](benchmark.md)) | 우리 | Tiny |
|---|---|---|
| 아무것도 안 보내는 연결 하나를 열어 둔 채 다른 요청 | 200, 0.0003초 | 5초 타임아웃, 그 뒤 종료 (SIGPIPE) |
| 대상 9,000바이트 GET | 431, 서버 계속 | 종료 (SIGABRT) |
| 20MB 받는 중 클라이언트가 끊음 | 서버 계속 | 종료 |
| 4KB 파일, 연결 재사용 없음, 동시성 100 | 약 4.8만 요청/초 | 약 1.1만 요청/초 |

처리량 차이를 poll 하나의 효과로 읽으면 안 된다. Tiny 는 연결마다 `getnameinfo`·`printf`, 파일마다 `mmap` 을 하고 우리 서버는 하지 않는다.

## 2. 동시성 모델

| 방식 | 연결 하나당 | 장점 | 대가 |
|---|---|---|---|
| 반복 서버 (Tiny) | 없음, 한 번에 하나 | 가장 단순 | 느린 연결 하나가 전부를 막음 |
| 연결마다 `fork` | 프로세스 | 연결끼리 메모리 격리 | 생성 비용, 자식 정리(`waitpid`), 상태 공유가 어려움 |
| 연결마다 스레드 / 스레드 풀 | 스레드 | 코드가 블로킹 그대로라 읽기 쉬움, 여러 코어 | 공유 상태 잠금, 스레드 스택 메모리, 경쟁 상태 디버깅 |
| `select` | 이벤트 루프 | POSIX | fd 번호 상한(`FD_SETSIZE`), 매번 집합을 다시 만듦 |
| **`poll` (우리)** | 이벤트 루프 | POSIX 라 macOS·Linux(glibc, musl)에서 같은 코드, fd 번호 상한 없음 | 매 바퀴 전체 연결을 훑음(O(n)), 코어 하나 |
| `epoll` / `kqueue` | 이벤트 루프 | 준비된 fd 만 받음, 연결이 많을 때 유리 | OS 마다 API 가 다름 (Linux / BSD·macOS) |

**고른 이유**: 4.5일·3명 일정에서 CI 5개 조합(Ubuntu·Alpine·macOS)을 한 코드로 통과해야 했고, 블로킹 서버를 나중에 이벤트 루프로 갈아엎는 비용을 피하려고 처음부터 `poll` 로 시작했다. 스레드와 `fork` 를 쓰지 않아 잠금과 자식 정리가 필요 없다.

**대가**: 코어 하나만 쓴다. 요청 처리 중 오래 걸리는 계산이 있으면 그동안 다른 연결도 기다린다. 동시 연결 상한은 1024 이고, 동시성 1000 측정에서는 닫히는 중인 연결까지 상한에 닿아 실패가 생겼다 (설계대로 유지).

## 3. 동적 처리 방식

웹서버가 "파일이 아닌 응답"을 만드는 방법들이다.

| | CGI | FastCGI | 서버 안 함수 (우리 앱) | Reverse Proxy (우리 프록시) |
|---|---|---|---|---|
| 실행 단위 | 요청마다 `fork`·`exec` | 상주하는 워커 프로세스 | 서버 프로세스 안 | 별도 서버 (우리는 같은 바이너리) |
| 통신 | 환경 변수 + stdin/stdout 파이프 | FastCGI 프로토콜 (소켓) | 함수 호출 | HTTP (소켓) |
| 요청당 비용 | 프로세스 생성 | 낮음 | 가장 낮음 | 연결 하나 더 + 파싱 한 번 더 |
| 격리 | 프로세스 단위 | 프로세스 단위 | 없음 (앱이 죽으면 서버도) | 프로세스·기계 단위 |
| 언어 | 아무거나 | 아무거나 (라이브러리 필요) | 서버와 같은 C | 아무거나 (HTTP 만 말하면 됨) |
| poll 루프와 맞물림 | 파이프·`waitpid` 를 논블로킹으로 다뤄야 함, 실수하면 루프가 멈춤 | 소켓이라 무난, 프로토콜 구현 필요 | 계산이 길면 루프가 멈춤 | 소켓이라 무난 |
| 확장 | 한 기계 안 | 워커 수 조절 | 없음 | 백엔드 추가 + 분산 |

**고른 것**: 간단한 계산(`/api/add`, `/api/echo`)은 함수로, 확장은 Reverse Proxy 로. CS:APP Tiny 의 `serve_dynamic` 이 CGI 라 출발점은 CGI 였지만, poll 루프 안에서 파이프와 자식 프로세스를 다루는 위험을 일정 안에 지지 않기로 했다 ([decisions.md](decisions.md) 2026-11-20). FastCGI 는 프로토콜을 하나 더 구현해야 하는데, 같은 "상주 프로세스에 소켓으로 넘긴다"는 이점을 HTTP Reverse Proxy 로 얻을 수 있었다.

**대가**: 앱 코드는 서버와 같은 프로세스라 격리가 없고, 앱을 바꾸려면 서버를 다시 빌드해야 한다. 프록시 경유는 백엔드 직접 호출의 약 40% 처리량을 보였다 (업스트림 연결을 요청마다 새로 열기 때문으로 보지만 단계별로 나눠 재지는 않았다).

## 4. 정적 전송

| 방식 | 하는 일 | 장점 | 대가 |
|---|---|---|---|
| `read` → 버퍼 → `write` | 파일을 메모리 버퍼에 읽어 보냄 | 단순 | 파일 크기만큼 메모리, 버퍼 관리 |
| `mmap` 한 번 (Tiny) | 파일 전체를 매핑해 `write` 로 다 보냄 | 복사 한 번 줄임 | 다 보낼 때까지 블로킹, 보내는 중 파일이 줄면 SIGBUS |
| **`pread` + `write` 조각 (우리)** | 16KB 이하 지역 버퍼로 한 조각씩, 막히면 루프로 | 메모리 일정, 논블로킹 루프와 맞음, POSIX | 사용자 공간 복사가 한 번 있음 |
| `sendfile` | 커널 안에서 파일 → 소켓 | 사용자 공간 복사 없음 | Linux 와 macOS 의 시그니처·동작이 다름, POSIX 아님 |

**고른 이유**: 이식성 규칙(POSIX 범위, OS 분기 최소화)과 논블로킹 루프에 맞는 "한 번에 한 조각" 모양. 응답 헤더는 버퍼로, 본문은 파일 오프셋으로 진행 상태를 저장해 short write 를 이어 보낸다.

**곁가지 교훈**: 헤더와 본문을 따로 `write` 하다 보니 Nagle 알고리즘과 상대의 지연 ACK 가 맞물려 keep-alive 정적 파일 요청마다 약 44ms 씩 멈췄다. 받은 연결마다 `TCP_NODELAY` 를 켜서 해결했다 (#43).

## 5. nginx 와 다르게 정한 것

비슷한 기능을 가진 운영 서버와 기본값·동작이 다른 곳이다.

| 항목 | nginx | 우리 서버 | 이유 |
|---|---|---|---|
| 경로의 `//` | `merge_slashes on` (기본으로 합침) | 기본 400, `--merge-slashes` 로 합침 | 라우팅과 파일 경로가 다른 문자열을 보는 우회를 기본에서 막음 ([decisions.md](decisions.md) 2026-11-23) |
| 프록시 접두사 | `proxy_pass` 에 URI 를 주면 접두사를 바꿈, 안 주면 그대로 | 항상 그대로 (정규형) | 판정한 경로와 백엔드가 받는 경로를 같게 |
| 다음 백엔드로 넘기기 | `proxy_next_upstream error timeout` 기본, 보낸 뒤의 non-idempotent 요청은 넘기지 않음 | 기본 꺼짐, `failover=` 를 주면 connect 단계에서만 | 요청 바이트가 나간 뒤에는 어떤 메서드도 다시 보내지 않음 |
| 죽은 백엔드 쉬기 | `max_fails=1 fail_timeout=10s` 기본 | failover 라우트에서 10초 (`PROXY_BACKEND_DOWN_MS`) | 비슷한 값 |
| 백업 백엔드 | `server ... backup` | `backup=host:port` | 같은 개념 |
| 업스트림 연결 재사용 | `keepalive` 로 가능 | 요청마다 새 연결, `Connection: close` | 응답 경계를 단순하게 (중계 끝 = 연결 끝) |
| 프로세스 모델 | 마스터 + 워커 여러 개, epoll·kqueue | 프로세스 하나, poll | [2. 동시성 모델](#2-동시성-모델) |
| chunked 요청 본문 | 지원 | 501 | 일정 안의 범위 밖 |
